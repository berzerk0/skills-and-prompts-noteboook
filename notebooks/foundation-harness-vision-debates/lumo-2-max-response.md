# Response from: Lumo
Part 1: What's buildable today vs. what's an open problem
Already solved (at least partially) in existing systems:

Detecting whether a task needs a multi-step plan: Planner-executor architectures are well-established. LangChain's Plan-and-Execute agents, AutoGPT's task decomposition, and OpenAI's function calling with structured outputs all handle this. Claude Code and Cursor already do rudimentary "this needs a plan" detection.
Knowing when to use git, shell commands, etc.: Tool-use frameworks (function calling, tool calling APIs) are mature. Claude's computer use, GitHub Copilot Workspace, and Devin all demonstrate structured tool orchestration.
Not running dangerous commands: Sandboxing, permission systems, and command allow-listing are solved engineering problems. Docker containers, gVisor, and tools like Claude Code's permission prompts address this.
Self-recovery via breadcrumbs/checkpoints: Agent state persistence exists in LangGraph (checkpointing), CrewAI (memory), and others. The concept of writing intermediate state to disk and resuming is implemented, though it's brittle in practice.
Communicating with other models: Multi-agent message passing is implemented in frameworks like CrewAI, AutoGen (Microsoft), and LangGraph. The mechanics of passing messages back and forth are solved.
Making scripts and knowing where output goes: Any agent with filesystem access and tool calling can do this. The quality of the scripts is another matter, but the mechanical capability exists.
Logging its own performance: Eval frameworks and tracing (LangSmith, Weights & Biases traces, Phoenix by Arize) capture agent runs for post-hoc analysis. Writing reflection notes and re-injecting them as context is implementable via RAG over past sessions.

Partially explored but not reliably solved:

Recognizing when to create a new skill/agent/prompt template vs. using existing ones: This is a meta-cognitive judgment that no system does well autonomously. Frameworks like DSPy optimize prompts programmatically, but deciding "this task warrants a new persistent artifact rather than just handling it inline" requires judgment that current models don't consistently make. You'd be building on shaky ground here.
Knowing how subagents should communicate with each other (protocols, shared state, logfiles): Multi-agent coordination is an active research area. AutoGen and CrewAI provide patterns, but they're far from optimal. The "right" communication topology is task-dependent and nobody has a principled framework for choosing one automatically. See the multi-agent literature — Park et al.'s generative agents (2023), the AutoGen paper (Wu et al., 2023), and Microsoft's recent frameworks — none solve agent-to-agent protocol selection.
Clarifying ambiguous user intent: Some work on this (clarification questions in dialogue systems, CHAI's human-AI interaction guidelines), but no coding agent reliably detects when it needs more information vs. when it should just proceed. Most either over-ask or barrel ahead.
Self-improvement from past failures: Reflexion (Shinn et al., 2023) demonstrates LLM agents learning from verbal feedback in subsequent trials. But this is episodic and fragile — translating "X failed due to Y" into durable behavioral change that survives across session types is not demonstrated convincingly anywhere. You'd be extending, not implementing.

Genuinely unsolved / aspirational:

Recognizing when to expand the harness itself: This is the big one. It requires the agent to possess accurate metacognition about its own architecture — knowing what skills it lacks, what artifacts it should create, and whether creating them is worth the cost. This is essentially the problem of automated capability acquisition, which is an open frontier in AI research. Nobody has this working reliably. You'd be inventing from scratch.
Knowing principles for the models it uses and that they don't behave the same: Model-aware routing and behavior adjustment is nascent. People hand-tune prompts per model (e.g., Anthropic's prompt engineering guides differ from OpenAI's). An agent that automatically adapts its strategy based on which model it's running is not something anyone has built well.
Balancing contradictions between principles: This is moral/practical reasoning under conflicting constraints — a hard problem in philosophy that doesn't have algorithmic solutions. You can build heuristics, but "knowing how to balance contradictions" in general is AGI-adjacent territory.
Expecting reasonable performance even from weak models: Robustness to model quality is the holy grail of agent design. The entire field is currently struggling with the fact that agentic systems are extremely model-sensitive — a system that works with GPT-4 often falls apart with GPT-3.5-tier models. Nobody has a principled solution beyond "use a better model."
Critical thinking without sycophancy: This is an alignment/training problem more than an architecture problem. Model behavior is shaped by RLHF/RLAIF. You can nudge it with system prompts, but you can't architect your way around a model that was trained to please.


Part 2: Where you're fooling yourself
"It" doesn't know anything. You keep saying "it knows" — it knows when to make a skill, it knows how subagents communicate, it knows when to sound the alarm. But you acknowledged at the end that "models aren't magic, they just predict tokens." These two statements are in tension. What you're describing is a system where a model predicting tokens makes reliable architectural decisions about its own design. That's the hardest part of what you're describing, and it's where you're most likely to hit the wall. The capability you need is metacognition — a model reasoning accurately about what it can't do — and models are notoriously bad at calibrating their own limitations. They'll confidently create a skill that's useless, or fail to create one they desperately need.
"Based on principles more than specifics" is doing enormous lifting. You say the harness is flexible because it operates on principles. But principles have to cash out into specific behaviors somewhere. "Be efficient" is not actionable — "prefer batched tool calls when possible, collapse sequential reads into a single grep" is. The translation from principle to behavior is where all the difficulty lives, and you've offloaded that translation to the model itself, which is exactly the part that doesn't work reliably yet.
The self-expansion loop has no guardrails in your vision. If the harness can create new agents, skills, scripts, and prompts, you've created an ecosystem that grows without bound. Who audits the artifacts it creates? A model-generated subagent that hallucinated its prompt template is now a permanent part of your system. You mention "good research or the user's previous written down instructions" as the basis for decisions, but you don't describe any verification step. In practice, you'd accumulate cruft — dead skills, overlapping agents, scripts that were created for a one-off task and never cleaned up. This is a software maintenance problem, and autonomous systems are terrible at self-maintenance.
"Leave logs for itself on how it did" assumes accurate self-assessment. A model that failed because it misunderstood the user's intent will write a log entry that says "failed due to ambiguity in the request" when the real failure was a reasoning error on its part. Garbage-in self-reflection produces garbage-out self-improvement. Reflexion works in constrained environments (ALFWorld, HotPotQA) where success is binary and externally verified. Coding tasks rarely have clean success signals — "did this work?" is often itself a judgment call that the failing model is unequipped to make.
Cross-model communication is underspecified. "It knows how to talk to other models" — through what protocol? Different models have different context windows, different tool-calling formats, different strengths. A subagent running a weaker model might not understand a message formatted for a stronger one. You need a message schema, a capability negotiation layer, and error handling for messages that exceed a target model's competence. This is distributed systems engineering, not just "pass messages back and forth."
The "knows when to use paragraphs vs. bullet points" line reveals a trap. This sounds trivial but it's symptomatic of the whole vision: you're asking the model to make stylistic judgments reliably and consistently. It won't. This will work 70% of the time and produce jarring mismatches 30% of the time, and there's no clean way to improve that ratio without hardcoding rules (which defeats the "principles not specifics" goal).
Self-recovery from zero context is harder than you think. "Enough breadcrumbs for a session with 0 context to pick it back up" — this requires the breadcrumbs to be written in a format that a fresh model instance can interpret correctly without any of the context that motivated them. This is essentially the problem of writing documentation for a codebase, except the "documentation" is written by an LLM mid-task, under time pressure, about its own reasoning process. LLMs are bad at this. The breadcrumbs will be incomplete, misleading, or reference things that aren't captured. You'll get partial recovery at best.

Part 3: What doesn't cash out
"It knows when to sound the alarm." What does this mean operationally? Alert the user via what channel? With what urgency threshold? And critically — if the model could reliably detect that something is going wrong, it would often be able to fix it, which obviates the alarm. The cases where you most need an alarm are the cases where the model doesn't realize it's in trouble. This is the same calibration problem.
"It knows when contradictions between principles exist and how to balance them." Name a contradiction you expect to encounter. I bet when you try to specify it, you'll find it reduces to either "follow priority order X" (which is just a rule, not balancing) or "use judgment" (which is offloading to the model with no mechanism). There's no middle ground that's both principled and implementable.
"It is solid enough in its design to expect reasonable performance even from weak models." This doesn't cash out because "reasonable performance" is undefined, and the mechanism for achieving it is "solid design" — which is circular. What specific design choices make a system robust to weak models? Strong type-checking? Conservative tool permissions? Restricted action spaces? Each of those trades off against flexibility, which is the thing you're trying to preserve. You can't have both without a very specific architecture you haven't described.
